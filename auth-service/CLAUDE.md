# CLAUDE.md — auth-service

Service-specific context. Read the root [`../CLAUDE.md`](../CLAUDE.md) first — it covers the JWT shared-secret contract, identity headers, and the `account.created` event this service publishes.

## Purpose

Owns account identity: credentials, OAuth linking, token issuance, and session lifecycle. Does not own user profile data (bio, avatar, settings) — that's `user-service`, kept in sync asynchronously via the `account.created` event, not a synchronous call.

## Code map

- `src/auth/auth.controller.ts` / `auth.service.ts` — the HTTP surface (register/login/refresh/logout/sessions) and its orchestration logic.
- `src/auth/jwt/jwt-token.service.ts` — signs/verifies access + refresh JWTs. Access and refresh tokens use **different secrets** (`JWT_ACCESS_SECRET` vs `JWT_REFRESH_SECRET`) — don't conflate them when touching this file.
- `src/auth/token/token.service.ts` — shared token-issuance path used by every login flow (password, every OAuth provider) so cookie behavior and session persistence stay identical across them. Also owns the OAuth handoff-code signing (separate secret again, `OAUTH_HANDOFF_SECRET` — see `PROBLEMS.md` for why its current fallback is unsafe).
- `src/auth/token/refresh-token.service.ts` — session persistence. Revocation is implemented by **deleting** the row, not by setting `revoked`/`revokedAt` — those columns exist in the schema but nothing in the codebase ever sets them to true (see `PROBLEMS.md`).
- `src/account/` — plain CRUD around the `Account` model, deliberately kept separate from `auth/` so both the password flow and the OAuth flow can share it.
- `src/oauth-account/` — one Passport strategy + guard per provider (`strategies/`, `guards/`), plus `oauth-account.service.ts` which finds-or-creates the `Account` and links the provider identity. This is the **other** place (besides `auth.service.ts#register`) that publishes `account.created` — the two call sites send different field sets (see `PROBLEMS.md` and root `PROBLEMS.md` item 5).
- `src/outboxEvent/` — `outbox-event.service.ts` (write side, called inside the same `$transaction` as account creation) and `outbox-relay.service.ts` (`@Interval(2000)` poller that publishes to RabbitMQ and marks rows `success`/`failed`).

## Conventions specific to this service

- **ESM imports use explicit `.js` extensions** even in `.ts` files (e.g. `from "./auth.service.js"`) — this is required by the `"type": "module"` + TS setup in `package.json`/`tsconfig.json`, not a mistake to "clean up."
- **Never hand-edit `src/generated/prisma/`.** It's regenerated by `npx prisma generate` from `prisma/schema.prisma`; it's gitignored for a reason.
- **Account creation must stay transactional with its outbox event.** Both `auth.service.ts#register` and `oauth-account.service.ts#loginWithOauth` write the `Account` and the `OutboxEvent` in the same `prisma.$transaction([...])` call. If you add a new way to create an account, keep this pattern — it's what guarantees the event is never silently lost.
- **Don't add fields to the `account.created` payload without checking `user-service`'s consumer.** The payload shape is duplicated by hand in two places in this service and in `user-service/src/consumer/consumer.service.ts`'s `AccountCreatedPayload` interface — see root `CLAUDE.md` contract #3 and this service's `PROBLEMS.md`.
- **Global `ValidationPipe`** (`whitelist: true, forbidNonWhitelisted: true, transform: true`, set in `main.ts`) rejects any request body field not declared on the target DTO. New DTO fields need `class-validator` decorators or they're silently stripped (or the whole request rejected, if `forbidNonWhitelisted` catches an unknown field).

## Where to look before changing things

- Anything about token secrets/expiry → `src/auth/jwt/jwt-token.service.ts` + this service's `.env.example` + root `CLAUDE.md`'s shared-secret note.
- Anything about what fields a registration flow sends downstream → both `auth.service.ts#register` (password) and `oauth-account.service.ts#loginWithOauth` (OAuth) — they are not currently kept in sync, so check both before assuming one reflects the other.
- Session/logout behavior → `refresh-token.service.ts`. Note the `revoked`/`revokedAt` columns before relying on them (see `PROBLEMS.md`) — actual revocation today is row deletion.
- Current known issues → `PROBLEMS.md` in this directory.
